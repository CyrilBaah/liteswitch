# Design: LiteSwitch, the simplest version that wins

Generated by /office-hours on 2026-11-26

## Problem Statement
Visitors on slow (<=3G) or Data-Saver connections pay real money per MB and often give up before a heavy page loads. Browsers already report the connection (`navigator.connection`, `Save-Data`), but most sites ignore it. LiteSwitch serves a lite page to those visitors, and a Flagsmith Experimentation A/B test checks the hypothesis: **for slow or Data-Saver visitors, the lite page makes more of them start the lesson than the full page does.**

## What Makes This Cool
- The footer "data-cost receipt" turns an abstract metric into money: "This page used 6.4 MB ≈ X CFA" next to "0.3 MB ≈ X CFA". It's the 10-second demo moment.
- The experiment targets the people who actually feel the cost. Fast visitors are never enrolled, so the result answers the real question instead of being averaged away by fiber users.

## Constraints
- **Live with the experiment running by Fri 2026-11-27 12:00 GMT.** Submit by Sun 2026-11-29 12:00 GMT (hard deadline 14:30).
- Next.js App Router + TypeScript on Vercel, Flagsmith Cloud free plan with Experimentation (beta).
- The owner must be able to explain every file. Secrets go only in `.env.local` and Vercel env vars.
- SDK method names come from the Flagsmith docs only. Verified 2026-11-26 in [run-an-experiment](https://docs.flagsmith.com/experimentation/run-an-experiment) and [clients/javascript](https://docs.flagsmith.com/clients/javascript):
  - `@flagsmith/flagsmith@^12.4.0`. `init` must include `enableEvents: true` (it throws otherwise).
  - `identify(userId, traits?) => Promise<IFlags>` (traits are `string | number | boolean`).
  - **Normal read, records nothing:** `flagsmith.getAllFlags().page_weight`, then `flag?.experiment?.inExperiment` and `flag.variant` ("Evaluate with the SDK's normal flag call instead, which records nothing, then record the exposure yourself").
  - **Exposure:** `flagsmith.trackExposureEvent('page_weight', { value: flag.variant })`. It's only shown in examples (no formal signature), and exposures are deduplicated per identity.
  - Conversions: `flagsmith.trackEvent(name, { value })`. Flush: `await flagsmith.flushEvents()`.
  - **Not used:** `getExperimentFlag` (it records the exposure at evaluation time, which is the wrong moment for us).
  - **Fallback** if `trackExposureEvent` misbehaves in testing: call `getExperimentFlag('page_weight')` (sync in the browser example) at the moment the variant is committed to the DOM, after `identify` has resolved, and never after the timeout fired.

## Facts that shape the design (from the docs and the web, 2026-11-26)
- Results show "Collecting data" until a variation has **≥50 identities** (≥5 conversions for occurrence metrics). Bayesian engine: lift, 95% credible interval, win probability.
- An experiment is a % rollout over the identities that evaluate the flag. Segment targeting isn't confirmed in the current docs.
- An environment needs a **warehouse** (Flagsmith-managed on Cloud) before you can create an experiment. The first events can take **a few hours** to appear. Refresh results at most once every 5 minutes.
- Each identity counts once, in the first variation it saw. Conversions count only after its exposure. Event names are case-sensitive and must exactly match the metric.
- Every variation needs a key. `control` is reserved for the flag's own value. Starting an experiment locks the flag.
- Chrome removed Lite mode in 2022, so `Save-Data` rarely fires anymore. `effectiveType` is what actually puts people in the segment. Safari/iOS and Firefox report nothing ("unknown").

## Premises (agreed)
1. The win is a real experiment with real slow visitors, not code polish. Recruiting starts today, in parallel with the build.
2. Only slow visitors enter the experiment, gated in code. Fast and unknown visitors get the full page and never record an exposure.
3. No monorepo. The reusable part is one folder, `lib/liteswitch/`, inside the app.
4. Keep the data-cost receipt, and also send `trackEvent('page_bytes', { value: bytes })`, so Flagsmith reports bytes per variant. No separate logging system.
5. No embeds, no custom font work. Lite skips the web font.
6. Heavy media sits **above** the Start button, and `lesson_started` fires only once the lesson content is actually visible. That way the metric captures people who leave during a heavy load.
7. *(User addition)* Don't depend only on real recruits. From Friday afternoon, a Playwright simulation runs against a separate Flagsmith **Simulation** environment to guarantee ≥50 identities per variation. Real and simulated results are **always reported separately**.

## Approaches Considered
### Approach A: Client decides (CHOSEN)
The server renders a light shell; the client detects the connection, and only slow visitors read `page_weight` and record an exposure (normal read + `trackExposureEvent` when the variant is committed). Details below.
### Approach B: Server decides (rejected for now, roadmap item)
Client hints (`Accept-CH`/`Critical-CH: ECT, RTT, Downlink`) plus `@flagsmith/nodejs`, sending only the chosen variant's HTML. Rejected because the Node exposure method isn't quoted in the docs (it would mean guessing) and per-identity SSR caching on Vercel is risky in 36 hours.
### Approach C: Two static pages + client redirect (rejected)
The redirect costs a 3G round-trip, which is the exact waste being fought, and the content would be duplicated.

If it's missing (first paint raced the cookie), it generates a UUID client-side, sets the cookie with the same attributes, and reads it back. | `lib/flags.ts` | Flagsmith init with the env key baked into the deployment (see Simulation). ### Measuring bytes
- **All media is same-origin**, served from `/public` on Vercel, so `transferSize` is populated. No third-party CDN, so no Timing-Allow-Origin problem.
- `transferSize = 0` for a cache hit is **correct** for a data-cost receipt: cached bytes cost the visitor nothing.
- `page_bytes` has two biases that pull in **opposite** directions. A streaming video's later range requests may be undercounted, which understates full-page bytes. Lost `pagehide` beacons come mostly from early leavers, who on the full page downloaded little, so losing them *overstates* the full arm's average. **The net direction is unknown.** We measure the beacon-loss rate per arm (`page_bytes` count ÷ exposure count) and report it next to the byte numbers. The write-up says exactly this.

### Events (same `ls_vid` identity for all of them)
- `lesson_started` (**primary**): sent when Start is clicked. The "Loading lesson…" gate **starts after the variant is resolved**. The button is enabled only once the intro content is visible: the headline plus the first media element's first frame (full) or poster (lite). This is how heavy sites behave, and it's what premise 6 needs.
- `lesson_completed` (secondary): sent on Mark complete.
- `page_bytes` (value metric): total bytes, sent once.
- Call `flushEvents()` on `pagehide` so 3G visitors who leave quickly still report.

### Flagsmith setup (in the UI, before any code is deployed)
- Project `liteswitch` with environments **Production** and **Simulation**. Turn on the Flagsmith-managed warehouse in **both**.
- Multivariate flag `page_weight`. Control value = full JSON `{"video":"autoplay-hd","images":"hd","fonts":"web","embeds":true}`. One variation with key `lite` = `{"video":"tap-to-load-360p","images":"low-lazy","fonts":"system","embeds":false}`. Split 50/50, rollout 100% (the code already limits it to slow visitors).
- Metrics: `lesson_started` (primary), `lesson_completed`, `page_bytes` (value).
- Segment `slow_or_saver` (net_type in slow-2g,2g,3g OR save_data = true). It's used **after** the experiment, to roll the winner out to slow visitors only.
- Create and start the `page_weight` experiment **in both environments**, with the same variations, split and metrics. Start each one only after its deployment has *sent* a test exposure and a `lesson_started` (with no errors in the network tab). Don't wait for the events to *appear* in Flagsmith, which can take hours.
- **Checkpoint: Fri 09:00 GMT** for the Production test event being sent. Fallback if it slips: start the experiment the moment the event is sent, even after 12:00. The site is still "live" on time, and the submission states the actual start time. Simulation must be started before the simulation run (Fri afternoon).

### Simulation (a separate deployment, never the production URL)
- **Isolation:** a dedicated Vercel deployment from a `sim` branch, with its own env vars: the **Simulation** environment key and `NEXT_PUBLIC_SIM_MODE=1`. The production deployment doesn't contain the Simulation key at all, and ignores `?net=`. A real visitor can't land in the Simulation population by clicking a link. Turn on Vercel Deployment Protection for the sim deployment, so only the script (with a bypass token from `.env.local`) can reach it.
- Chromium + CDP network throttling (a realistic 3G profile, e.g. ~400 kbps / 400 ms RTT) so load times are real. On the sim deployment only, `?net=3g` forces the slow tier.
- Each simulated visitor gets a new context (a new `ls_vid`) and a **patience budget** drawn at random from 3-15 s. It clicks Start only if the button is enabled within its budget; otherwise it leaves. A fixed share then clicks Mark complete. The result comes from real load times against simulated patience. It is not a scripted outcome, and the write-up says so in exactly those words.
- Target: ≥60 identities per variation, run Friday afternoon. Results are reported **separately** from Production.

## Implementation notes (2026-11-26, first build)
- **`proxy.ts`, not `middleware.ts`.** Next.js 16 renamed Middleware to Proxy (same job). See `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`.
- **Env vars:** `NEXT_PUBLIC_FLAGSMITH_ENVIRONMENT_KEY` (Production key on main, Simulation key on sim) and `NEXT_PUBLIC_SIM_MODE=1` (sim deployment only; it enables `?net=`).
- **SDK calls** were checked against the `@flagsmith/flagsmith@12.6.0` type definitions: `init({ environmentID, enableEvents: true, identity, traits })`, `getAllFlags()`, `trackExposureEvent`, `trackEvent`, `flushEvents`. The SDK sends events with plain `fetch` (no sendBeacon/keepalive), so we flush right after every event.
- **Video bytes:** browsers don't report a streaming video until it has fully downloaded, so the receipt estimates video bytes as file size × buffered fraction (`<video data-bytes>`; sizes in `app/lesson/media-sizes.json`, written by `scripts/make-media.sh`).
- **Start gate** applies to enrolled visitors only. Visitors who aren't enrolled can start right away, so iOS Low Power Mode (which never preloads video) can't lock anyone out.
- **Dev-only test hook:** `npm run dev` + `?variant=lite|full` shows a variant without Flagsmith. It is never enrolled, and it is off in production builds.
- **Measured locally (headless Chromium, production build for full):** full = **6.50 MB** (video 5.85 MB, images 297 KB, font 47 KB, JS ~150 KB). Lite media = **37 KB** (poster 8 KB + JPEGs 29 KB). The lite total is about 0.19 MB with the same ~150 KB of JS, a **~34× gap**. Tapping lite's video adds 0.24 MB.
